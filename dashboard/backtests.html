ⓘ
Every optimizer run publishes up to two entries. Same run, same full continuous price history, same simulator — what differs is which set of parameters was replayed.
  • <run>_full — the train-best genome (best_config.json): whatever scored highest on the data the optimizer was allowed to see. It has looked at that data, so its full-history total is in-sample and flattering.
  • <run>_oosbest_full — the OOS-best genome (holdout_best_config.json): the candidate that scored best on the held-out segment the optimizer never trained on. Only published when that holdout came back clean (no liquidation, positive growth), which is why there are fewer of them.
Both are then replayed over the whole history — so an _oosbest_full headline number still contains the in-sample era. The honest figure for it is its holdout stat, not its total %. Treat the total as "how this genome would have done overall", and the holdout as "what it did on data it had never seen".
Which one runs live: "Adopt OOS-best" on the Optimize page builds the config from holdout_best_config.json — the _oosbest_full genome. Adopting reads the run, not the entry you clicked, so picking a _full row does not get you the train-best genome.
Router/combo entries (_fcfs_full, _fcfs_wf, _router_full) are neither: they have no genome of their own — their components do. For those, _fcfs_full = every component always eligible (matches live behaviour) and _fcfs_wf = causal walk-forward with the roster gate (the honest estimate).
